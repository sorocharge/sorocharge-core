# Protocol currency and the live event-shape check

`verify_transfer_effects` in `sorocharge-signer` deliberately encodes the
event shape the **live** Soroban host emits for a SEP-41 transfer, rather
than only the shape the CAP text describes — the two have not always
matched. That assumption is re-checked on a schedule by
[`.github/workflows/event-shape-check.yml`](https://github.com/sorocharge/sorocharge-core/blob/main/.github/workflows/event-shape-check.yml),
because a protocol upgrade can change emitted events without changing any
of this workspace's types or breaking its compilation.

## Last live verification

Verified **2026-11-20**:

| Network | RPC endpoint | Protocol version | Latest ledger |
|---|---|---|---|
| Testnet | `https://soroban-testnet.stellar.org` | **30** | 5,836,793 |
| Pubnet | `https://mainnet.sorobanrpc.com` | **29** | 65,584,312 |

Current RPC servers do not expose a `getLedger` method; the protocol
version is reported by `getLatestLedger` (and `getNetwork`) on the same
endpoint. Testnet runs one protocol ahead of pubnet, so it is the network
the scheduled check targets.

The workspace pins, verified to support both protocol versions:

| Crate | Pinned version |
|---|---|
| `stellar-xdr` | `=30.0.0` |
| `stellar-rpc-client` | `=30.0.0` |
| `stellar-strkey` | `=1.0.0` |
| `@stellar/stellar-sdk` (dev-only golden vectors) | `17.2.0` |

`stellar-xdr` 30.0.0 carries the CAP-71 `AddressV2` and delegated-signer
(`AddressWithDelegates`) credential variants this library builds, signs, and
verifies; the `address_v2_transfer` and `delegated_transfer` golden vectors,
generated by the pinned SDK, exercise both.

## What the scheduled job does

Monthly, and on demand (`workflow_dispatch`), the job:

1. Reads the pinned `stellar-xdr` major version from `Cargo.toml` and fails
   if testnet's live protocol version is newer — the pinned XDR would then
   be behind the network.
2. Runs
   `cargo run -p sorocharge-signer --example check_live_event_shape`, which
   funds two throwaway testnet accounts through Friendbot, submits a real
   native-SAC `transfer`, and runs `verify_transfer_effects` over both the
   simulation's diagnostic events and the executed transaction's contract
   events from ledger meta.
3. On any failure, fails the run **and** opens (or comments on) an issue
   labelled `ci-alert`, so a shape drift is not only visible to whoever
   reads the Actions tab.

No key is stored or read from the environment: the example generates fresh
keypairs per run, and Friendbot funds them with testnet lumens only.

To run the check by hand:

```sh
cargo run -p sorocharge-signer --example check_live_event_shape
```

`SOROCHARGE_TESTNET_RPC_URL` and `SOROCHARGE_TESTNET_FRIENDBOT_URL` override
the defaults.
